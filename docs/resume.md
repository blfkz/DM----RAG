## 一、投递版(简历"项目经历"栏直接粘贴)

**项目名称**:电商智能问答 RAG 系统(企业级)| **角色**:项目负责人(需求分析 / 架构设计 / 技术选型 / 测试验收)

**项目概述**(一段话):
基于 LangChain 从零搭建的企业级电商知识库 RAG 问答系统:支持 6 种格式商品文档入库与自动清洗分块,采用"向量 + BM25"混合检索(RRF 融合)和提示词防幻觉约束,回答均带引用溯源;实现多用户认证、会话持久化、权限隔离与数据统计;自研压测工具实测 100 人并发成功率 99%、平均响应 3.47 秒,60 项单元测试全部通过。

**主要工作**(5 条要点,每条都有数据):
1. **设计并实现 RAG 全链路**:文档解析(6 格式)→ 中文分块(500 字/80 字重叠,中文标点分隔)→ 云端向量化 → 混合检索(BM25 + 向量,RRF 融合取 top6),单次检索约 0.16 秒,精确型号词与语义近义词双路命中
2. **解决大模型幻觉问题**:提示词硬约束(只依据资料作答)+ 参考资料预编号引用机制;模型漏标引用时按句子相似度自动溯源兜底,确保每个回答都有可见的原文依据
3. **企业级性能优化**:流式输出、混合检索、云端批处理、哈希去重、会话摘要压缩、SQLite WAL 等 10 项;自研 Python 多线程压测工具(临时库隔离 + 费用确认门),实测 100 人并发成功率 99%、平均响应 3.47 秒、吞吐 5.2 问/秒,瓶颈归因到云端限流
4. **多用户系统与安全设计**:PBKDF2-HMAC-SHA256 加盐哈希(30 万次迭代)、会话级权限隔离、admin 角色管控、操作日志审计
5. **工程化实践**:60 项 pytest 单元测试(覆盖 7 组核心模块)、git 版本管理与云端备份、Docker 部署配置、数据清洗专项(pandas 4 条规则清洗脏电商数据,空值删除/超长截断/去重/乱码过滤)

## 四、面试必答题速览(骨架答案,面试前展开练习)

**Q1:为什么用 RAG 而不是微调大模型?**
RAG 知识可随时更新(上传新文档即生效)、成本低、答案可溯源防幻觉;微调适合把领域知识"内化"进模型权重,但更新慢、成本高、还说不清答案依据。电商商品资料天天变,RAG 是更工程化的选择。

**Q2:怎么防止大模型瞎编(幻觉)?**
三层防线:①检索层——模型只能看到检索出的真实片段;②提示词层——硬约束"只依据资料作答,资料不足必须明确说找不到",且片段预编号让模型"抄编号"而非自己数;③引用层——解析校验编号,漏标时按句子相似度自动溯源兜底,保证每个回答都有原文依据。

**Q3:混合检索为什么比纯向量检索好?**
精确型号词(如"星耀X1")向量模型容易泛化丢字面,BM25 字面命中更准;语义近义词(如"续航"≈"电池")BM25 匹配不了,向量行。两路各取 top20,用 RRF(业界标准排名融合算法)合并去重取 top6,取长补短。

**Q4:100 人并发压测怎么做的?结果说明什么?**
自研 Python 多线程压测工具,5 个场景(网页抽查/单发基线/热身/100 人主场景/并发登录),用 Barrier 让 100 个请求同时打出制造真实峰值;数据写临时库、正式数据零污染。结果:99% 成功率、平均 3.47 秒;失败 6 次全部是云端免费额度的 QPS 限流——证明瓶颈在云端而非本地链路,这正是"纯云端 AI + 本地轻量服务"架构的预期,购买更高配额即可突破。

**Q5:项目里最大的技术难点是什么?**
两个:一是引用可靠性——大模型自己数编号不可靠,最后用"预编号 + 抄编号 + 解析校验 + 相似度溯源兜底"闭环解决;二是压测定位瓶颈——发现百炼向量接口批上限 10、SDK 重试放大延迟等细节,通过分阶段计时(检索/生成/引用/落库)把延迟归因到具体环节。
